ppf-contact-solver → LightWave Migration Plan

Embedding the ZOZO CUDA contact solver (ppf-cts-capi C ABI) into the LightWave workspace at E:\lw.
Strategy: prove the integration in a console sandbox app first, then promote to a LightWave .p plugin.

Source repo: E:\code\open_source\forks\ppf-contact-solver  •  Target repo: E:\lw  •  Date: 2026-06-16

1. Goal & strategy

Get the solver running inside the LightWave build system with the smallest possible first step, then climb to a real plugin.

The C ABI and the final-link recipe are already proven by the standalone Phase-0 spike (crates/ppf-cts-capi/spike/): a C++ host links three libraries and solves a pinned cloth on a real GPU, penetration-free, for 30 frames. The migration does not re-prove the solver — it proves that the same link recipe works under premake5 / the Jahley app framework, with the CRT and CUDA settings the LightWave repo imposes.

Two-step climb
  1. Console sandbox (apps/sandbox/PpfContactSolver) — a copy of HelloWorld. No LightWave SDK, no UI. Just: does the lib link and the GPU solve run inside E:\lw's build? this plan
  2. LightWave .p plugin — once the sandbox is green, wrap the same calls in a plugin (Displacement/Master) driving real LightWave geometry. later

4. Compatibility risks (resolve before / during sandbox)

#RiskSeverityResolution
1 CRT mismatch. The spike linked /MD (dynamic CRT). LightWave sets staticruntime "On" = /MT. Rust staticlibs default to the dynamic CRT (/MD-equivalent). Mixing /MT and /MD in one link is the classic LNK2038 / duplicate-symbol failure. high Pick one CRT for the whole link. Two options:
(a) Build the Rust capi with the static CRT: RUSTFLAGS="-C target-feature=+crt-static", then the sandbox keeps staticruntime "On". Cleaner, matches lw convention.
(b) Override the sandbox to staticruntime "Off" (/MD) to match the spike, and ship the VC++ redist DLLs. Faster to first-light, deviates from lw norm.
Recommend (a); fall back to (b) if +crt-static surfaces issues with the backend DLL.
2 cudart static vs dynamic. lw apps link cudart_static; the spike linked dynamic cudart.lib + shipped cudart64_12.dll. The backend DLL has its own CUDA runtime regardless. med The backend DLL is self-contained (loads cudart64_12.dll at runtime). The sandbox itself does no CUDA, so it needs no cudart link of its own for the solver path. Keep it simple: link nothing CUDA in the app; just ship cudart64_12.dll next to the .exe for the backend DLL. Only add cudart_static if the app grows its own CUDA code.
3 Vendored windows.0.52.0.lib drift. Its path lives deep in the cargo registry and changes with crate versions. low Copy it into the vendored dep folder (§5) at build time and link by explicit path, so lw never reaches into the cargo registry.
4 Eigen header collision. lw bundles a stripped eigen34 (CPU-only) on its include path; the CUDA backend needs full Eigen 3.4.0. none here Non-issue for the sandbox: Eigen is compiled into the prebuilt backend DLL. The sandbox only #includes the C header ppf_cts.h, which pulls no Eigen. Just don't add the solver's C++ sources to the lw build.
5 Solver log noise. SimpleLog dumps a full advance trace per step to stdout. cosmetic Fine for the sandbox proof. Quiet it before the plugin / any CI harness.

5. Where the dependencies go (vcpkg static triplet)

The solver is a prebuilt-only dependency — no premake5.lua of its own (nothing to compile), just headers, libs, and the runtime DLLs. As built, the artifacts live in the vcpkg static triplet that lw_common.lua already wires onto every consumer's include + lib path. This was chosen over a hand-made lw_thirdparty/ppf_cts/ folder so the sandbox needs no custom includedirs/libdirs at all — only links{}.

E:\lw\lw_thirdparty\vcpkg\installed\x64-windows-static\
├── include\
│   └── ppf_cts.h                      // from crates/ppf-cts-capi/include/
├── lib\
│   ├── ppf_cts_capi.lib               // from target/release/ (+crt-static)
│   ├── libsimbackend_cuda.lib         // from .../src/cpp/build/lib/
│   └── windows.0.52.0.lib             // vendored from cargo registry
└── bin\                               // created manually: static triplet ships no bin/
    ├── libsimbackend_cuda.dll         // staged next to the .exe at build time
    └── cudart64_12.dll                // from %CUDA_PATH%\bin\
Convention choice (resolved). lw_common.lua already adds the vcpkg static triplet's include + lib (Release), debug/lib (Debug), and CUDA v12.9/lib/x64 to every consumer's search paths. By dropping the solver artifacts into that triplet, the sandbox premake5.lua declares only links{} — no explicit includedirs/libdirs, no touching shared build files. The vcpkg static triplet has no bin/ directory, so one is created by hand to hold the two runtime DLLs; a postbuild step copies them next to the .exe. (A hand-made self-contained lw_thirdparty/ppf_cts/ folder was prototyped and rejected in favor of this.)

6a. premake5.lua (as built — Release-only)

Because the artifacts live in the vcpkg static triplet that lw_common.lua already adds to the include + lib paths, the project declares no custom includedirs/libdirs — just the bare clone plus a Release links{} block and a postbuild DLL-staging step. Release-only: the Rust capi always links the release CRT (libcmt); there is no libcmtd, so a /MTd Debug app cannot statically link it (see Risk #1).

// ... bare HelloWorld-clone header (kind, location, files, staticruntime "On") ...
    dofile(path.join(ROOT, "apps/buildTools/app_common.lua"))

    local VCPKG_BIN = path.join(ROOT,
        "lw_thirdparty/vcpkg/installed/x64-windows-static/bin")

    filter "configurations:Release"
        links {
            "ppf_cts_capi", "libsimbackend_cuda", "cudart", "windows.0.52.0",
            // native-static-libs not already linked by app_common:
            "ntdll","advapi32","cfgmgr32","credui","gdi32","msimg32",
            "secur32","user32","winspool","userenv","dbghelp",
            "legacy_stdio_definitions",
        }
        postbuildcommands {
            '{COPYFILE} "' .. VCPKG_BIN .. '/libsimbackend_cuda.dll" "%{cfg.targetdir}"',
            '{COPYFILE} "' .. VCPKG_BIN .. '/cudart64_12.dll" "%{cfg.targetdir}"',
        }
    filter {}

app_common.lua brings in AppCore, mace_core, g3log, opengl32, Ws2_32, C++20, the static runtime, and — via lw_common.lua — the vcpkg static triplet include/lib paths and the CUDA toolkit lib path. So the project only declares the solver-specific links{} and stages the DLLs. (cudart resolves to the import lib in CUDA v12.9/lib/x64; the matching cudart64_12.dll is staged for the backend DLL.)

8. After the sandbox: the .p plugin

The sandbox proves linking + solving under lw's build. The plugin step (separate plan) then adds, on top of that same dependency:

  • Plugin class & registration (ServerRecord, ModuleDescriptor) — likely a Displacement handler (per-frame vertex write-back) or a Master/LayoutGeneric driver.
  • Geometry bridge: LightWave mesh ↔ the flat vertices/faces arrays ppf_cts_set_geometry expects; pin selection ↔ ppf_cts_set_pins; LightWave motion ↔ ppf_cts_update_pin_targets.
  • Frame loop owned by LightWave's evaluation instead of a for loop.
  • Build kind changes from ConsoleApp to a .p shared lib (see plugins/ + the LightWave SDK skill); the solver link recipe is unchanged.
Key insight that de-risks the whole effort: the solver is consumed purely through the C header ppf_cts.h and three prebuilt libs. Nothing about the sandbox → plugin transition touches the solver, CUDA, or Eigen. Once the sandbox links and runs, the plugin is “the same calls, different host.”
